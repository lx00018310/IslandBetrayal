> **核心目标：让“移动 → 自动战斗 → 获得收益 → 组队 → 背叛爆箱 → 争抢”成为清晰、爽快、可理解且可验证的体验闭环。**

## 0. 执行原则（必须遵守）

1. **最小改动，不重构玩法。**优先修改表现层和 UI；默认不修改 `simulation.ts` 中的战斗、数值、AI、缩圈、Boss、无限模式、存档与状态机。只有在真实验证发现规则 Bug 时，才允许局部修正并补测试。
2. **先审计现有能力，再写代码。**不得把已存在的功能重复实现；使用现有 ForgeAX 原生正交体素管线、资产/场景包、实体池、事件字段和测试脚本。
3. **操作约束不变。**PC：WASD/方向键移动 + Space 交互；手机：虚拟摇杆 + 唯一常驻交互按钮；自动攻击保持。**不要增加 Dash/翻滚/攻击专用按键**，也不要把 `dash: false` 擅自改为新操作。
4. **保持玩法与表现分离。**视觉动画、镜头阻尼、粒子、短暂“顿帧感”均仅作用于表现，**不得暂停模拟时钟、伤害结算、联网同步或碰撞判断**。
5. **不新增重量级依赖。**不引入 Three.js/R3F 渲染替换、新 Shader 框架、SSAO、Tilt-Shift、物理引擎、复杂音频系统、数据分析后端；仅使用项目已支持的原生组件。现有正交相机**没有需要设置的透视 FOV**。
6. **不泄露背叛意图。**视觉提示只反映真实发生或玩家能够观测到的行为；不凭 AI 性格、内部仇恨值或未来决策提前标记“叛徒”。
7. **一次只修改一个体验问题。**每阶段形成可运行提交及前后对比证据；未验证的工作不得写成“已完成”。

### 对原 Gemini Plan 的处理

- **保留思想**：可读性、手感反馈、接地感、事件反馈与节奏设计。
- **不直接执行**：透视 FOV 25–30、SSAO、Tilt-Shift、全场 Hit Stop、强制地图扩容、移动速度 +50%、新增 Dash 按键、全量 3D 血条替换 DOM、所有升级经验改成实体拾取、重新拆角色层级。
- **原因**：这些内容与现有架构、操作约束或已经落地的功能存在冲突，且缺少真实试玩证据；不应通过叠加特效掩盖问题。

## 2. 最终验收定义（先定义，后实施）

### A. 体验验收（优先级最高）

第一次接触游戏的玩家在不看开发文档的前提下，应能：

1. **前 10 秒**知道怎么移动，观察到角色在自动攻击，并理解攻击命中了谁（10 秒为测试目标，不保证每局都按时出现怪物）。
2. **前 30 秒**至少一次明显感受到击杀或成长反馈，能区分金币/宝物收益与 XP/升级收益。
3. **前 60 秒**在出现候选伙伴时能够理解“靠近→邀请/接受→已组队”的变化。
4. **发生背叛/断线/破箱时**，能一眼看出事件起因与结果，识别可拾取战利品的落点，并知道接下来可以争抢。
5. **全程**看得清自己、队友、敌人、危险预警；手机竖屏下不因 UI/特效遮住角色和重要信息。

这些是**待验证目标**，而非目前已经达成的结果。若随机对局中某事件未发生，用场景化测试触发，不要为了强凑时间改动 AI/规则。

### B. 工程验收

- 旧玩法结果与存档格式不变；组队、Space 主动解盟、外部破箱、两场 Boss、缩圈、无限模式均可正常推进。
- 不新增卡死、重复事件反馈、刷新后异常、隐形碰撞、移动输入延迟。
- 保留既有单测、类型检查、ForgeAX 检查和端到端脚本通过；新增的表现行为要有最小测试。
- 对比同设备、同场景的前后性能；帧时间/流畅度不应明显退化。若不满足，首先降级非必要特效，而不是改模拟规则。
- 有前后截图、约 90 秒真人操作录屏或观察记录（如运行环境不能录制，记录缺失并交接人工验收）。

## 3. 分阶段执行任务（严格按顺序，单阶段过门槛再继续）

### P0：建立可比较基线——不改玩法（必须先做）

**目的**：区分“已经实现但不好看”“实际未呈现”“事件顺序/时机不对”“手机卡顿”。

**执行项**：

1. 拉取最新 `main`，记录 HEAD、工作区状态；如果用户有未提交改动，不清空、不覆盖。
2. 运行现有 `test`、`typecheck`、`project check` 和 `playthrough`，记录实际结果；不把未运行写成已通过。
3. 在 **1280×720 桌面**与 **390×844 竖屏**记录下列截图或短视频帧：
   - 开局 5–10 秒的移动/战斗；
   - 一次击杀与升级收益；
   - 邀请和组队成立；
   - 一次 Space 主动解盟/爆箱或外部破箱；
   - 缩圈与 Boss 危险提示。
4. 建立简短审计表，逐条记下：**已有/缺失/存在但不明显/有 Bug/无法验证**；至少指出 3 个最影响体验的画面时刻，并标注截图路径。
5. 检查移动端是否能真实进入游戏、触控操作是否稳定；当前环境无真机就明示“未验证”，不能以桌面窗口缩放代替。

**交付**：`docs/reviews/experience-baseline-2026-11-13.md`（截图可放既有 `docs/reviews/`；文件名允许顺延执行日期）。

**通过门槛**：明确至少 1 个可复现的体验问题，且 P1 的修改可对应该问题；若 P0 未发现问题，先不盲目批量加特效。

### P1：打通“移动→自动战斗→收益”10～30 秒闭环（最优先代码修改）

**目标**：第一次玩的用户感觉“我在操控，我打中了，我得到了东西”，而不是观赏背景动画。

**实施建议**（按 P0 问题选最小项，不要求全部新增）：

1. **移动与镜头**：保留正交相机和输入/碰撞规则。在 `presentation.ts` 现有跟随点上，小范围试验仅表现层的、与 `dt` 无关的阻尼跟随（推荐先比较无阻尼与约 `0.06~0.12s` 的视觉追随）；有必要时再做小幅移动方向前瞻。优先保证急停、折返、窄屏时不晕、不拖尾、不丢失危险目标。
2. **命中反馈**：先复用现有 `hitFlash` 和 debris；若命中反馈仍不明显，只加一项低成本强化，如目标局部闪光/轻微击退视觉/简短命中音效（前提：ForgeAX 音频资源链已有可靠实现）。禁止冻结整局模拟或为每次命中创建一批永久实体。
3. **收益反馈**：保持当前 XP 规则和宝物实体掉落规则不变。缺乏辨识度时，在既有 HUD 或局部轻提示中用不同文字/颜色表达“+XP / 获得宝物”，并保持提示有界、可合并，避免刷屏。
4. **初始可玩性检查**：在实际运行中验证初始自动攻击、第一只怪的出现位置、击杀所需时间、升级入口。若某项存在**真实 Bug**，只修对应逻辑并新增回归测试；不因为 Gemini 提议而重写攻击体系。
5. **可读性**：优先确认现有自己的 HP HUD、怪物受击效果、友敌身份环可辨认。只有屏幕证据明确显示“必须依赖头顶 HP 才能理解战斗”时，才加轻量血条；优先对近距离关键目标显示，不给全部远处怪物常驻高成本 3D Sprite。

**代码落点**：优先 `assets/island/presentation.ts`、`assets/ui/guide-controller.ts`、必要时 `assets/guide.ui.css`；资产缺口才碰 `art.pack.ts`。只在实测规则 Bug 情况下碰 `simulation.ts`。

**P1 通过标准**：移动不增加明显操作迟滞；一次命中、击杀、获得奖励能被首次试玩者看出来；旧自动攻击、经验成长与存档无回归。

### P2：把“组队→背叛爆箱→争抢”打磨成项目招牌事件

**目标**：让合作收益与背叛风险有因果可读性，不把背叛仅做成一团漂亮的爆炸。

**只改三种真实事件的反馈顺序**：

| 事件 | 发生前：可读前兆 | 发生瞬间：明确反馈 | 发生后：行动指引 |
|---|---|---|---|
| 组队成功 | 靠近/邀请可见，按钮操作含义清楚 | 两个角色身份环/连线切换，宝箱成立（优先复用） | 看得懂队友是谁、共享财富在增加 |
| 主动解盟/超距断线 | 距离线危险颜色与断线规则可理解 | 连线断开＋宝箱爆散；反馈不得重复触发 | 明确金砖散落位置及可以争抢 |
| 外部攻击破箱 | 目标宝箱受击/危险可见 | 宝箱破裂效果与掉落数量一致 | 明确队伍仍可能维持、战利品可以拾取 |

**执行项**：

1. 复用 `presentation.ts` 的关系环、组队光束、`lastBreakEvent`/`chestBreaks` 真实变化、既有 debris 池；**事件只触发一次**，重开、刷新、第一帧加载不能误触发旧事件。
2. 优先调整 **时序和强弱层次**：普通击中反馈小，组队反馈中，真实爆箱反馈最强；特效不能遮挡掉落物、角色或危险预警。音效如有现成链路可做一个最小统一入口；没有就不因此开发整套音频系统。
3. 组队以后，不只是变绿，还要能持续识别队友和宝箱的关联；先复用脚底环、连线与现有 HUD。不要画遍布全屏的永久连接线或不必要 3D UI。
4. 背叛表达必须对玩家公平：只能在**事件已经发生**时表现“背叛”；AI 的贪财、记仇或背叛倾向只能通过已发生的行为推测，不能提前用红骷髅等图标泄露。
5. 不擅自修改掉落资产总量、外部破箱分配比例、是否保留队伍、距离阈值或收益数值。若视觉与真实逻辑不符，应修视觉映射，不先改规则。

**代码落点**：`assets/island/presentation.ts`、`assets/island/art.pack.ts`（仅必要的材质/实体复用）、`assets/ui/guide-controller.ts`。

**P2 通过标准**：由不了解代码的人看一次事件录屏，能分别判断“组队成立 / 主动或被动断线 / 外部破箱”及可拾取物的落点；事件与现有模拟数值一致。

### P3：检查遭遇节奏，而不是直接把地图扩大 3～10 倍

**目标**：验证玩家是否经常只是在跑图，还是缺少可理解的操作窗口；**先测量，后调参**。

**实施建议**：

1. 仅在开发/测试输出中记录首次攻击命中、首次击杀、首次 XP/升级、首次遭遇其他角色、首次组队、首次断线/破箱的大致时间及相邻事件间隔。
2. 优先复用模拟状态差分/既有测试脚本，不做持久埋点平台、不上传玩家数据。若状态没有可靠区分依据，标注“不可直接测量”，不要伪造指标。
3. 用原始参数进行 **前 90 秒**测试：`0–10s` 掌握操作、`10–30s` 看懂收益、`30–60s` 体验合作或竞争、`60–90s` 感受到缩圈/博弈压力。**这只是体验假设，不是强制每局随机事件按时发生。**
4. 只有当测试表明“跑图占比过高、遭遇明显不足”时，才小幅试验单一变量（比如视野、初始刷怪区域、移动速度或地图局部布局），每次只改一个并 A/B 对比。**本轮默认不改 `GRID_SIZE`、缩圈时序与 AI 数量**。
5. 关注 AI 可读性：对 AI 角色的邀请、靠近、撤退、抢宝、背叛，优先让现有真实行为有可见反馈；不要新增复杂 AI 决策系统。

**建议记录的最小指标**：首次击杀秒数、首次升级秒数、首次与其他角色近距离遭遇秒数、首次组队秒数、首次破箱秒数、最长连续无有效互动时长、是否理解红/绿/黄状态。

**P3 通过标准**：有一张原始数据表和至少一条明确结论（保留地图/需要微调某一项/尚无足够证据）；不允许用“地图变大看起来更高级”作为单独验收理由。

### P4：性能、交互与真人试玩验收（正式收尾）

1. 运行项目原有 `test`、`typecheck`、`project check`、`playthrough`；补充最小测试覆盖：一次性事件触发、重开状态清理、摄像机参数稳定、手机画面无关键裁切。
2. 复验至少 **1280×720** 和 **390×844**；如可能再验横屏移动端。检查触控多指输入、Space 模态确认不连跳、UI 遮挡、掉帧、掉落物可见性。
3. 同设备、同画面、同特效密度比较修改前后 FPS/帧时间；能采集 p95 帧时间与 draw calls 则记录，采集不到就明说，不编造数字。若移动端明显卡顿，优先降低碎块密度、遮挡性 UI 或特效更新频率。
4. 至少 **3 名未参与开发的人**进行 5～10 分钟真实试玩（人数不足也可以进行，但不得宣称达到本门槛）。只问事实性问题：怎样组队？何时发生背叛？战利品属于谁？什么时候知道受到攻击？哪里让你想停下来？
5. 赛事要求的**真人累计有效体验 ≥900 秒**是单独的最终验收项，不可由自动推进、脚本时间或单纯挂机替代；若本轮尚未执行，写入遗留事项。
6. 对照 P0 截图/视频给出“改前 vs 改后”的相同事件对比；凡未明显改善的问题，记录原因并回退无效更改。

**P4 通过标准**：自动回归无新增失败；真人能够说清核心事件；性能没有明显劣化；文档与实际完成状态相符。

## 5. 最小测试矩阵

| 场景 | 必须看到/验证的结果 | 失败则优先检查 |
|---|---|---|
| 初始入场与移动 | 操控立即生效；镜头不抖、不丢主角 | 输入与表现层阻尼 |
| 怪物首次受击、死亡 | 命中可辨、收益可辨；怪物消失/掉落与真实状态一致 | `hitFlash` 与事件绑定 |
| 首次 XP/升级 | XP 数字和宝物收益不会混淆；升级可选择 | HUD 映射和暂停/确认 |
| 邀请、接受、已结盟 | 明确识别自己、队友、共享宝箱 | 关系环、连线、按钮状态 |
| Space 主动背叛 | 只触发一次爆箱；掉落可见；非提前曝光 | 事件 seq/状态差分 |
| 超距断线和外部破箱 | 行为结果不同但视觉都准确，外部破箱不错误解盟 | 规则到呈现映射 |
| 缩圈、Boss、结算 | 原有玩法正常、关键预警清晰 | 特效层级与主时钟 |
| 重开、刷新、无限存档 | 不残留上一局闪光/动画，继承数值未改 | 表现状态 reset 生命周期 |
| PC、手机竖屏 | 角色、提示、交互按钮可见；性能无显著下降 | Camera bounds / HUD 适配 |

## 6. 分次提交与交付规则

每个阶段结束按以下格式输出：

```text
阶段：P0 / P1 / P2 / P3 / P4
基准 commit：<sha>
修改文件：<文件列表>
本阶段解决的问题：<逐条列出>
保持不变的玩法逻辑：<明确说明>
自动化验证：<逐项 PASS / FAIL / 未运行>
人工试玩/性能：<实测数据或未验证>
证据：<截图、录屏、日志路径>
剩余问题：<具体问题，不虚报完成>
阶段提交：<commit sha，若未提交则说明>
```

提交建议：P0 只提交审计文档；P1、P2、P3 分别小提交；P4 收尾验证。**未经用户明确要求，不修改远端仓库或强制推送**；本地 AI 可以按其授权的正常工作流本地提交。

### 终止/回退条件

出现以下任一情况时，停止继续叠加效果，优先回退该阶段：

- 输入响应变慢、镜头令人不适或敌我/红圈信息更难看清；
- 破坏自动攻击、Space 组队/解盟、Boss、缩圈或存档；
- 命中/爆箱反馈重复触发或事件前提前暴露 AI 意图；
- 低端设备性能明显劣于基线；
- 仅增加代码量，却无法用截图、试玩或数据证明改善。

## 8. 本轮明确不做（防止范围蔓延）

- 真正多人联机、房间匹配、网络同步与反作弊；
- 重做完整美术风格、替换全部模型、添加高成本后处理；
- 扩大地图 10 倍或重新设计整个缩圈系统；
- 新增技能键、冲刺键、复杂组合操作；
- 更改无限模式全局词条/长期传承系统；
- 重新设计 AI 性格、背叛概率或经济模型；
- 自建数据埋点服务、音频引擎或独立物理粒子引擎。

**最终验收不是“加了多少新特效”，而是首次试玩者能否顺畅操作、读懂收益与背叛，并且愿意继续下一局。**
